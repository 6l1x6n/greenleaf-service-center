# Сайт сервис-центра Greenleaf

Одностраничный сайт на статике + Cloudflare Worker: каталог с наличием в реальном времени,
заказы с резервированием, бронирование товаров, даты поставок, презентации и заявки на
партнёрство. Все формы отправляются в ваш Telegram-бот.

## Структура

```
worker.js              — Cloudflare Worker (формы → Telegram, заказы, остатки, админка)
index.html             — страница (все секции)
css/style.css          — стили
js/                    — ui.js (модалки/тосты), catalog.js (каталог), forms.js (отправка заявок)
data/                  — JSON-данные (правятся парсером или суперадмином)
admin/                 — Decap CMS (админка по адресу /admin)
scripts/parser/        — парсер каталога из портала поставщика (Python)
_redirects             — редиректы (в т.ч. /admin/* → /admin/index.html)
_headers               — заголовки кеширования (data/* без долгого кеша)
.github/workflows/     — deploy.yml (push → деплой), parse-catalog.yml (парсер)
```

## Деплой (только через git push)

1. Запушьте изменения в `main` — GitHub Actions (`deploy.yml`) развернёт ровно git HEAD.
2. Один раз добавьте в секреты репозитория **`CF_API_TOKEN`** (Cloudflare → My Profile →
   API Tokens → Create Token → «Edit Cloudflare Workers» → Account: ваш, Workers Scripts: Edit).
3. Проверка после деплоя: `bash scripts/verify.sh` (сверяет `/version.json` на сайте с git HEAD).

⚠️ Ручной `wrangler deploy` из рабочей копии **не** рекомендуется: авто-деплой по пушам
(в т.ч. от парсера) перезальёт origin/main поверх. `scripts/deploy.sh` откажет, если копия
отстаёт от origin/main.

## 2. Telegram-бот (приём заявок)

1. Откройте в Telegram [@BotFather](https://t.me/BotFather) → `/newbot` → придумайте имя → получите **токен**.
2. Напишите вашему боту любое сообщение (например, «привет») — это нужно, чтобы он мог вам писать.
3. Узнайте свой **chat id**: откройте в браузере
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates`
   и найдите число в поле `"chat":{"id":...}` (обычно 10 цифр).
4. В Cloudflare Pages: **Settings → Environment variables** добавьте:
   - `TG_BOT_TOKEN` = токен из BotFather
   - `TG_CHAT_ID` = ваш chat id
5. Передеплойте сайт (Deployments → … → Retry deployment). Готово — заявки приходят вам в Telegram.

Проверить локально: установите [Wrangler](https://developers.cloudflare.com/workers/wrangler/) (`npm i -g wrangler`), затем
`npx wrangler pages dev .` в папке проекта — сайт и функция поднимутся на `localhost:8788`.

## 3. Кабинет (вход: сайт → «Войти»)

Кабинет СЦ/суперадмина — `cabinet.html`: филиалы, остатки, заказы, поставки,
мероприятия, каталог, заявки. Вход — только для СЦ и суперадмина.
Пароли портала и кабинетов в KV зашифрованы (Worker-секрет `DATA_ENC_KEY`).

Decap CMS (`/admin`) — опционально, нужен свой OAuth-провайдер (GitHub OAuth App +
Cloudflare Worker `vencax/netlify-cms-github-oauth-provider`); в `admin/config.yml`
укажите `repo`, `base_url` и `auth_endpoint`. Основные правки делаются в кабинете.

### Настройки сайта (Обзор → «⚙️ Настройки сайта»)

- **Партнёрские ID** — коды вида `kz12345678`, которым положена партнёрская цена
  (−50 %). Список хранится на сервере (KV `site_settings.partnerIds`), в коде сайта
  его нет: чужим кодом скидку не получить. Дополнительно можно задать Worker-секрет
  `PARTNER_IDS` (`kz11111111,kz22222222`) — работают оба источника.
- **Логин партнёра для парсера** — или Worker-секрет `PARTNER_LOGIN`.
- **Показывать скидочные цены в каталоге** — если выключено, скидка не показывается
  И не применяется к заказу (каталог, корзина и сервер считают одинаково).

## 4. Парсер каталога (автоматический)

Каталог собирается с портала поставщика **greenleaf-global.com** (описание алгоритма —
`PARSING_GUIDE.md`): вход в кабинет СЦ → раздел покупки → партнёр `kz44326234` →
перебор страниц «Показать еще...» → разбор строк (`код ABC123`, название, кол-во
«Доступно для продажи», скидочная цена × 2).

### Расписание — каждые 2 часа днём (Астана)

10:00, 12:00, 14:00, 16:00, 18:00, 20:00, 22:00, 00:00 (Астана) =
`0 5,7,9,11,13,15,17,19 * * *` UTC. Перед прогоном — случайная задержка 0–3 мин
(защита портала), между этапами — паузы.

### Умный парсинг (все запуски)

- **Существующие артикулы** — обновляется только количество (и статус), если оно изменилось.
  Название, цена и фото не перезаписываются (правка — через панель суперадмина или `--full`).
- **Новые артикулы** (в любом запуске, не только утром) — карточка создаётся один раз целиком:
  артикул, наименование, цена, фото, описание. В следующие прогоны — только количество.
- Каталог коммитится, только если реально изменился (пустые прогоны не деплоят сайт).
- Ручной полный прогон (перезапись данных существующих карточек): `python parser.py --full`
  или GitHub Actions → Parse catalog → Run workflow → флажок full.

### Фото товаров

Фото хранятся локально в репозитории (`assets/images/products/`, имя = артикул).
Парсер берёт вариант портала с наибольшим разрешением (оригинал до 800×800, веб-версия
«-shop» 600×600) и сжимает Pillow до 400 КБ / 800px (JPEG q82 для непрозрачных,
PNG для прозрачных). Файлы с низким разрешением (<400px, старые прогоны) и битые
перекачиваются автоматически (проход `upgrade_low_res_photos`, лимит 400 на прогон —
прогоны по расписанию добирают остаток).

**Разовое перекачивание всех фото в исходном разрешении** (`force_all_photos`):
включается флагом `--rephotos` (кнопка в Actions → Parse catalog → Run workflow)
или маркером `scripts/parser/.rephotos_pending` — следующий плановый запуск
выполнит проход сам. Все фото качаются заново (без фильтрации) в исходном
размере и сохраняются **байт-в-байт без сжатия**. После успеха маркер снимается —
дальше парсер работает по обычной логике и существующие файлы снова
**не перекачивает**.

Сайт читает каталог из `data/products.base.json` (виртуальный `/data/products.json`
с оверрайдами суперадмина отдаёт воркер):

### Фото товаров: оригиналы + превью

Рядом с каждым оригиналом парсер кладёт **превью** `<артикул>_card.webp` (WebP,
600 px, ~15 КБ). В карточку каталога подставляется именно превью: оригиналы
бывают по 18 МБ (PNG с прозрачностью), и страница каталога на 100 товаров тянула
~35 МБ картинок — на мобильном интернете каталог не открывался.

- парсер создаёт превью сам при скачивании/сжатии фото (`make_card_thumb`);
- разово пересобрать превью для всех товаров: `python3 scripts/parser/make_thumbs.py`
  (флаги `--force` — пересоздать, `--limit N` — ограничить количество).

```json
{
  "updated": "2026-08-04T12:00:00+03:00",
  "products": [
    {
      "id": "ABC123",
      "sku": "ABC123",
      "name": "Газонокосилка Greenleaf",
      "category": "Газонокосилки",
      "price": 28990,
      "image": "assets/images/products/ABC123.jpg",
      "status": "in_stock",
      "eta": null,
      "incoming": null
    }
  ]
}
```

Статусы считаются из количества: ≥ 6 — `in_stock`, 1–5 — `low`, 0 — `out`.
Категория определяется по ключевым словам в названии (словарь в конфиге).

### Автозапуск (GitHub Actions, каждые 2 часа)

Workflow `.github/workflows/parse-catalog.yml`: парсит каталог по расписанию, при
изменениях коммитит и пушит → авто-деплой обновит сайт автоматически.
Вручную можно запустить в любой момент: **Actions → Parse catalog → Run workflow**
(параметры: `task` all/products/deliveries, `full`, `skip_delay`).

Один раз добавьте учётные данные в секреты репозитория
(Settings → Secrets and variables → Actions → New repository secret):

| Secret | Значение |
|---|---|
| `SC_LOGIN` | логин кабинета СЦ (портал) |
| `SC_PASSWORD` | пароль кабинета СЦ (портал) |
| `PARTNER_LOGIN` | логин партнёра для портала (без него парсер не видит каталог) |
| `CF_API_TOKEN` | токен Cloudflare для деплоя (deploy.yml) |

### Локальный запуск (по желанию)

```bash
cd scripts/parser
cp config.example.json config.json   # впишите логин/пароль
pip install -r requirements.txt
python -m playwright install chromium
python parser.py                      # умный прогон (только количества + новые карточки)
python parser.py --full               # полный прогон (перезапись данных карточек)
```

`config.json` в `.gitignore` — секреты в репозиторий не попадут.

## 5. Заказы и остатки

- **Фактический остаток** — что последний раз сообщил парсер (`store-stock.json`).
- **«Ожидается» = 0 шт.** Так парсер помечает товар, которого на портале нет.
  Значит лимит резерва на такой товар действует (заказать 999 шт нельзя), а в
  кабинете он показывается как «Нет в наличии», а не «Нет данных».
- **Постоянная поправка остатка (дельта)** — KV `stock_deltas`: на сайте = факт
  парсера + дельта. В кабинете (СЦ и суперадмин) вводите нужное число — сохраняется
  разница к факту (бейдж «Δ −20» / «Δ +5» под полем остатка), и каждый следующий
  синк парсера сдвигает итоговое число на ту же разницу. Ручное значение держится
  **всегда**, пока его не снимут пустым полем (в т.ч. когда факт парсера стал
  0/«Ожидается» — дельта применяется поверх нуля; для товаров без факта парсера —
  абсолютное значение KV `stock_edits`, перекрывающее файл до сброса).
- **Зарезервировано онлайн** — товары в заказах `new`/`ready` (и 10-минутные холды корзины).
- **Доступно онлайн** = факт + дельта − холды − Σ `new`/`ready` − Σ `confirmed` после последнего синка.
- Статусы заказа: **⏳ Новый → 🟦 Готов к выдаче → ✅ Подтверждён** (или 🚫 Отменён).
  Подтверждение: резерв → продажа (остаток не меняется). После следующего синка парсера
  заказ уходит в архив и больше не влияет на остаток.
- Отмена заказа возвращает товар; удаление подтверждённого заказа НЕ возвращает товар.
- Раздел «🛒 Заказы» в кабинете: у СЦ — свои заказы, у суперадмина — все + архив;
  кнопки «Готов к выдаче»/«Подтвердить»/«Отменить» с необязательным комментарием для клиента.
- **«📦 Мои заказы» клиента** (без кабинетов): кнопка в шапке → модалка со своими
  заказами по токену устройства (`localStorage`, передаётся с заказом). Отмена — только
  пока заказ «Новый». Запрос к `/api/my-orders` — только при открытии модалки (без кеша).
- **Архивирование заказов** — по расписанию Worker (ежедневно в 03:23 UTC), а не
  запросом с сайта: анонимный GET раньше переписывал общую карту заказов и мог
  затереть только что созданный заказ.
- **Записи в карту заказов** идут через проверку с повтором (`mutateKvMap`): если
  параллельный запрос затёр нашу запись, она записывается заново.

## 6. Данные

- `data/store.json` — адрес, часы, телефон, WhatsApp (правьте через кабинет)
- `data/products.base.json` — каталог, обновляется парсером автоматически
- `data/store-stock.json` — остатки по филиалам (парсер)
- `data/deliveries.json`, `data/events.json` — поставки и мероприятия (через кабинет)
- `data/moves.json` — накладные/перемещения товаров (парсер)
- `assets/images/products/` — фото товаров (парсер качает и сжимает локально)
- Cloudflare KV (`SC_STORES`): оверрайды товаров/СЦ, заказы, брони,
  `stock_deltas` (поправки остатков), `stock_edits` (абсолютные остатки без факта парсера)

### Кабинет: заметки по работе с товарами

- Таблицы «Товары», «Наличие в СЦ» и «Остатки товаров» — **пагинация по 100 строк
  с нумерованным пейджером** (кнопки страниц слева, счётчик справа; «‹ Назад» /
  «Вперёд ›», окно из 5 номеров вокруг текущей с «…» при многих страницах;
  пейджер дублируется над таблицей и под ней, на мобильных — только снизу;
  поиск/фильтры сбрасывают на страницу 1). Несохранённые правки хранятся в буфере
  и переживают смену страницы; сохраняются кнопкой внизу.
- В «Наличие в СЦ» и «Остатках товаров» — **фильтр наличия** (✅ В наличии ≥6,
  ⚠️ Заканчивается 1–5, — Нет в наличии 0, 🕓 Нет данных) и **сортировка по остатку**
  по возрастанию/убыванию (товары без данных — в конец); фильтр и сортировка
  работают вместе с поиском и учитывают несохранённые правки буфера.
- «🧹 Сбросить мои правки» (и «Сбросить настройки этого филиала») — модалка с выбором,
  какие параметры вернуть к базовым данным (цены, описания, статусы, приоритеты,
  скидки, скрытие, настройки филиалов), с подтверждением.
- Публичный каталог — постраничный вывод по 100 товаров (нумерованный пейджер
  над и под списком, на мобильных — только снизу; страница в адресе `#page=N` —
  работают «назад/вперёд» браузера и прямые ссылки; при смене страницы список
  прокручивается к началу; фильтры/поиск сбрасывают на страницу 1).

## 7. Безопасность, лимиты и проверки

### Worker-секреты (Cloudflare → Workers → mygreenleaf → Settings → Variables and Secrets)

| Секрет | Зачем |
|---|---|
| `TG_BOT_TOKEN`, `TG_CHAT_ID` | заявки в Telegram |
| `AUTH_HMAC_KEY` | подпись токенов сессий кабинета |
| `DATA_ENC_KEY` | шифрование паролей портала и кабинетов (AES-GCM) |
| `STORE_CREDS` | учётки из раздела «Кабинет филиала» (для суперадмина) |
| `PARSER_API_KEY` | ключ парсера для `/api/parser-config` (только в заголовке `X-API-Key`) |
| `PARTNER_IDS` | белый список партнёрских ID (через запятую) — право на партнёрскую цену |
| `PARTNER_LOGIN` | логин партнёра для парсера (в коде репозитория его нет) |

Правила, которые закрыты в коде:

- партнёрская цена — только для ID из белого списка (формат ID больше не даёт скидку);
- пустой пароль и сбой расшифровки не дают войти в кабинет;
- пароль кабинета СЦ не уходит в Telegram (в чат — только обезличенные поля);
- лимиты на публичные записи: резерв 30/10 мин, места на мероприятие 10/час,
  регистрация СЦ 5/час, заявки 10/10 мин, вход в кабинет 10 попыток/15 мин;
- брони мест сверяются с лимитом мероприятия, заявки ограничены по размеру;
- клиент больше не может исключить чужие брони из расчёта остатка;
- строгий CSP (`script-src 'self'`), HSTS, `X-Frame-Options: DENY`, `nosniff` —
  inline-обработчики в разметке заменены делегированными слушателями.

### Проверки без деплоя

```bash
node scripts/worker-test.mjs   # 24 проверки API: цены, остатки, лимиты, заказы
node --check worker.js
python3 -m py_compile scripts/parser/parser.py
```

`scripts/worker-test.mjs` поднимает воркер в памяти с моками KV/ассетов и
проверяет: партнёрская цена по белому списку, «Ожидается» = 0, пустой пароль,
лимиты, типы заявок, ключ парсера только в заголовке, применение скидки,
сохранность заказов при параллельных запросах.

### Деплой

- `git push` в `main` → Actions → deploy.yml (воркер + статика) → `scripts/verify.sh`.
- После парсера деплой запускается только при успешном прогоне; каталог
  валидируется на валидность JSON перед коммитом, push идёт с `git pull --rebase`.
