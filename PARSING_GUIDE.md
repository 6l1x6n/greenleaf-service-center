# Парсинг каталога Greenleaf (scripts/parser/parser.py)

Документ описывает, как парсер собирает каталог товаров поставщика
GreenLeaf (greenleaf-global.com): остатки по Сервис-Центрам, цены, описания
и фото товаров, и как всё это попадает в репозиторий и на сайт.

Реализация: **`scripts/parser/parser.py`** (Python + Playwright + Pillow).
Запуск: **GitHub Actions** `.github/workflows/parse-catalog.yml` или локально.

---

## 1. Что делает парсер

- Входит в кабинет СЦ портала через **Playwright** (headless Chromium).
- Открывает раздел покупки товаров («Новая продажа») и перебирает каталог
  страницами («Показать еще…», до 200 страниц).
- Для каждой позиции извлекает: код, название, **количество в наличии**,
  цену, PV.
- Синхронизирует данные с постоянной базой `public/data/products.base.json`
  и производным `public/data/store-stock.json`.
- Скачивает фото товаров локально в `public/assets/images/products/`
  (качество: оригинал портала до 800×800, сжатие Pillow до 400 КБ;
  разово — исходники без сжатия, см. § 4).
- Собирает накладные (перемещения товаров) в `public/data/moves.json`.

Лог: «База товаров: N карточек…», «Каталог получен: N позиций»,
«Остатки по филиалам: […] -> store-stock.json», «Фото каталога (апгрейд): …».

## 2. Основные шаги алгоритма (`main()`, parser.py)

| Шаг | Где в коде | Что происходит |
|---|---|---|
| 1. Загрузка конфига | `load_config()` | `scripts/parser/config.json` (локально) или секреты Actions `SC_LOGIN`/`SC_PASSWORD` |
| 2. Полный список портала | `fetch_all_goods()` | Публичный API `/api/v1/shop/goods` (постранично limit=500, поля id, code, path, name, title, photo) — ~13 запросов |
| 3. Карточки каталога | `ensure_full_catalog()` | Для артикулов портала без карточки создаётся заглушка (status out, цена 0, фото — remote `-small` или плейсхолдер категории) |
| 4. Каталог каждого СЦ | `run_parse_store()` | `login()` → `open_shop()` → `scrape_goods()` (перебор строк и «Показать еще…») → `download_images()` → `merge_sc_items()` |
| 5. Накладные | `scrape_moves()` / `ensure_cards_from_moves()` | Перемещения центрального СЦ; для новых артикулов создаются карточки-заглушки (pending), достраиваются при появлении в каталоге |
| 6. Фото каталога | `fill_local_photos()` → `upgrade_low_res_photos()` | Досыпка локальных фото для карточек с remote-URL и апгрейд «мыльных» фото (см. § 4) |
| 7. Запись базы | `write_products()` / `write_store_stock()` | `products.base.json` + `store-stock.json`; изменения коммитит workflow |

Остановка/ошибки: таймаут workflow 60 мин; любые сетевые сбои этапов
логируются, прогон продолжает остальные этапы («— продолжаем»).

## 3. Какие поля парсятся (`scrape_goods` → `merge_sc_items`)

Строка каталога разбирается по ячейкам `<td>`:

| Поле | Обработка |
|---|---|
| **Код товара** | Строгий формат (например `ABC123`); нестандартные коды помечаются `skipped` |
| **Название** | Чистка `clean_product_name`: убирает `&nbsp;`, лишние пробелы, «Кол-во в коробке: N шт.» и суффиксы «Доступно для продажи: N» |
| **Количество** | Regex «Доступно для продажи: N» → `stock[sc_id]` по каждому Сервис-Центру |
| **Цена продажи** | `price = скидочная цена × price_multiplier` (мультипликатор по умолчанию 2), `partner_price = скидочная цена` |
| **Статус** | Считается из количества: ≥ 6 — `in_stock`, 1–5 — `low`, 0 — `out` |

**Режимы:**

- **«Умный» (по умолчанию, все запуски по расписанию)**: у существующих
  артикулов обновляется только количество (и статус). Название, цена и фото
  не перезаписываются — их правят через панель суперадмина или `--full`.
- **Новые артикулы** (в любом запуске) создаются целиком один раз: артикул,
  название, цена, фото, описание.
- **`--full`** (ручной): перезапись названий/цен/фото существующих карточек.
- **`--moves-only`**: только накладные (перемещения).

## 4. Фото товаров

Фото хранятся локально в репозитории: `public/assets/images/products/`
(имя файла = артикул, формат .jpg/.jpeg/.png; артикулы со слешем —
`ASF007/K` → `ASF007_K`).

Портал отдаёт несколько вариантов одного файла:

| Вариант | Что это |
|---|---|
| оригинал (без суффикса) | исходный файл, часто 800×800 (иногда с тяжёлыми PNG-метаданными) |
| `-shop` | веб-версия, обычно 600×600 |
| `-big` | «большая» версия, бывает 300×300 |
| `-small` | миниатюра 60×60 |

Логика скачивания (`download_best_image` + `download_product_photo`):

1. Пробуются варианты: оригинал → другие расширения оригинала → `-shop` → `-big`.
2. Скачивается вариант с **наибольшим разрешением** (ранняя остановка при
   ≥ 800px — сжатие всё равно ограничивает 800px).
3. Файл сжимается `compress_image_if_needed`: >400 КБ → до 800px по большей
   стороне; непрозрачные фото перекодируются в JPEG q82 (прогрессивный),
   PNG с реальной прозрачностью остаются PNG; метаданные вычищаются
   (Pillow-лимиты `MAX_TEXT_CHUNK`/`MAX_IMAGE_PIXELS` подняты для PNG
   с гигантскими текстовыми чанками портала).

**Апгрейд «мыльных» фото** (`upgrade_low_res_photos`): локальные файлы
меньше 400px по большей стороне (или битые) перекачиваются заново по полю
`photo` из API портала. Идемпотентно, лимит `photo_upgrade_limit` (400)
на прогон — прогоны по расписанию добирают остаток. Неудачные URL
помечаются `photo_404` и не повторяются. Аналогично `fill_local_photos`
(лимит `photo_fill_limit` 800) переводит карточки с remote-миниатюрами
на локальные файлы.

**Разовое перекачивание ВСЕХ фото в исходном разрешении** (`force_all_photos`):
однократный проход, включается флагом `--rephotos` или маркером
`scripts/parser/.rephotos_pending` (маркер лежит в репозитории — следующий
плановый запуск после обновления выполнит проход сам). Для каждого товара,
у которого портал знает фото (поле `photo` API-списка; коды без него —
по `image_url` из кэша листинга этого же прогона), файл скачивается заново
(`force`, без фильтрации по разрешению/наличию), берётся вариант
с наибольшим разрешением (оригинал → другие расширения → `-shop` → `-big`)
и сохраняется **байт-в-байт без сжатия** (исходное разрешение и качество
портала). Неудачные URL помечаются `photo_404`. Скачивание — urllib
в 8 потоках (публичные файлы, Playwright не нужен). После успешного прохода
маркер удаляется — дальнейшие запуски работают по обычной логике:
существующие валидные файлы **не** перекачиваются снова (только апгрейд
<400px с лимитом 400/прогон и досыпка новых артикулов).

## 5. Остатки по филиалам

- `public/data/store-stock.json` — производный файл: `{ updated, stock: { sc_id: { sku: "В наличии (N шт)" | "Ожидается" } } }`.
- Воркер (`worker.js`) на лету применяет к нему **постоянные поправки**
  (KV `stock_deltas`: на сайте = факт парсера + дельта) и списания
  (продажи/брони). Сам файл правки НЕ содержит — его перезапись парсером
  не затирает настройки админки.
- Ручное значение остатка держится **всегда**, пока его не снимут пустым
  полем (или не введут новое): для товаров с фактом парсера хранится дельта
  (применяется и когда факт стал 0/«Ожидается» — дельта поверх нуля);
  для товаров без факта — абсолютная правка KV `stock_edits`, которая
  перекрывает файл до сброса.
- Разница задаётся в кабинете (разделы «📦 Остатки товаров» и
  «📦 Наличие в СЦ»): вводите нужное число — система считает и хранит
  разницу к факту парсера (бейдж «Δ −20» / «Δ +5» под полем).

## 6. Запуск

### GitHub Actions (автоматический)

`.github/workflows/parse-catalog.yml`:

- **Расписание**: каждые 2 часа днём — 10:00, 12:00, …, 22:00, 00:00
  (Астана) = cron `0 5,7,9,11,13,15,17,19 * * *` UTC.
- **Защита портала**: случайная задержка 0–3 мин перед прогоном + паузы
  между этапами (5–15 с).
- Прогоны «умные»: существующие товары — только количества.
- Каталог коммитится (catalog-bot) и пушится только если реально изменился;
  пуш триггерит авто-деплой сайта (`deploy.yml`).
- Ручной запуск: **Actions → Parse catalog → Run workflow** (параметры:
  `task` all/products/deliveries, `full`, `rephotos` — разовое перекачивание
  всех фото, `skip_delay`).

Секреты репозитория: `SC_LOGIN`, `SC_PASSWORD`, `CF_API_TOKEN`.

### Локальный запуск

```bash
cd scripts/parser
cp config.example.json config.json   # впишите логин/пароль
pip install -r requirements.txt
python -m playwright install chromium
python parser.py                     # умный прогон (количества + новые карточки)
python parser.py --full              # полный прогон (перезапись данных карточек)
python parser.py --rephotos          # разовое перекачивание всех фото (оригиналы, без сжатия)
python parser.py --moves-only        # только накладные
```

`config.json` в `.gitignore` — секреты в репозиторий не попадают.

## 7. Ограничения и особенности

- Требуется доступ к greenleaf-global.com; партнёр для раздела покупки —
  `kz44326234`, учётка портала — из конфига/секретов.
- Каталог собирается до 200 страниц («Показать еще…»).
- Коды нестандартного формата пропускаются и попадают в статистику skipped.
- Фото обычных проходов качаются последовательно (sync-API Playwright не
  дружит с потоками), поэтому лимиты на прогон — 400/800 файлов; остаток
  добирают следующие прогоны. Разовый проход перекачивания всех фото —
  urllib в 8 потоках (без лимита, исходники без сжатия).
- Описания добираются инкрементально (`desc_limit` 80 на прогон).
- Если Pillow не установлен — фото сохраняются без сжатия (проверяйте размеры).
